# 组织治理方案

## 当前阶段

先维护一个能跑通的 `stock-research` 仓库。只有当数据、回测或部署形成独立发布周期后，再拆仓，避免产生一批只有 README 的空仓库。

## 目标仓库地图

| 仓库 | 职责 | 何时建立 |
|---|---|---|
| `.github` | 组织主页、仓库地图和安全政策 | 立即维护 |
| `requirements` | 研究范围、验收标准和开放问题 | 开始多人协作时 |
| `stock-research` | 当前端到端 MVP、因子与研究实验 | 已建立本地版本 |
| `stock-data` | 数据采集、版本、校验和查询 | 数据量或任务调度独立后 |
| `stock-backtest` | A 股成交规则和回测引擎 | 需要独立版本兼容后 |
| `portfolio-risk` | 组合优化、约束和归因 | 组合模型稳定后 |
| `deploy` | CI/CD、定时任务、监控和环境映射 | 首次部署前 |
| `execution` | 模拟盘、券商接口和交易风控 | 明确进入交易阶段后 |

## 第三方仓库政策

默认通过 `pyproject.toml`、锁文件和文档引用第三方项目，不为“收藏”而 Fork。

只有以下情况才保留 Fork：

1. 有必须长期维护的 A 股适配补丁；
2. 上游停止维护且组织愿意承担安全与兼容责任；
3. 需要固定审计版本且许可证允许；
4. 已配置上游同步、差异说明和自动测试。

每个保留的 Fork 应增加：

- `UPSTREAM.md`：上游地址、同步分支、版本和负责人；
- `PATCHES.md`：组织自有修改及原因；
- 定时上游同步检查；
- 现代 Python 版本的 CI；
- 许可证和数据再分发审查。

## 现有公开 Fork 的处理建议

- `daily_stock_analysis`：作为报告层，不作为研究真值；先同步上游。
- `akshare`：保留自定义数据任务前，修复缺失脚本并补测试；否则恢复纯上游依赖。
- `zipline`、`pyfolio`、`alphalens`、`empyrical`：评估迁移到 reloaded 系列。
- `ta` 与 `ta-lib-python`：二选一作为默认指标库，减少重复维护。
- `bt`、`Qlib`：明确一个主研究引擎，另一个只承担特定场景。
- `yfinance`：仅作为海外市场补充，不作为 A 股主数据源。

## 安全和合规

- GitHub 不存放券商密钥、付费行情和不可再分发的历史数据。
- 仓库只保存小型匿名样例，生产数据进入对象存储或数据库。
- 实盘功能必须与研究环境隔离，并保留人工审批、最大损失和紧急停止开关。
